# 建造系统性能优化建议

> 基于当前实现的静态分析（未做性能剖析实测），按"多大规模开始疼"排序。
> 涉及文件：`Plugins/BuildingCore/`、`Plugins/GameFeatures/Raft/`、`Plugins/GameFeatures/OceanAdventure/`。
> 记号：**N = 单个宿主上的建造件数量**，**H = 世界里已加载的宿主数量**。

---

## 0. 先说不用改的部分

不建造时，建造系统的每帧开销是 **0**：

- `UBuildStructureComponent` 只在 `BuildDebug 1` 时开 tick
- `UBuildStructureVisualComponent` 不 tick，只监听 `OnStructureChanged`
- `UBuildPreviewComponent` 只在建造模式下 tick

所以"世界里有 100 条建满的船"本身不产生建造系统的开销。常态成本来自宿主 Actor 自己
（浮力 tick、网络休眠策略），见第 3 节。

## 1. 热点清单

| # | 位置 | 复杂度 | 何时开始疼 |
| --- | --- | --- | --- |
| 1 | `UBuildStructureComponent::CollectSnapCandidates` | **每帧 O(N)** | 单宿主 > 500 件 |
| 2 | `UBuildStructureVisualComponent::RebuildInstances` | 每次结构变化 O(N) + 渲染状态重建 | 同上 |
| 3 | `UBuildStructureComponent::RebuildIndex` | 每次写入 O(N)，**批量恢复累计 O(N²)** | 读档 1000+ 件 |
| 4 | `UBuildStructureComponent::ComputePieceBounds` | 每次结构变化 O(N) | 同 3 |
| 5 | `UBuildStructureComponent::WouldStayConnectedWithout` | 每次拆除 O(N) BFS + 两个 TSet 分配 | 拆除手感变钝 |

共同根因：**"每次变化就重算全部"**。这在 P0 的几十件规模下是正确取舍（简单、无状态、不会不同步），
到几千件就不成立了。下面每条都给出增量化的修法。

### 1.1 候选集缓存（优先级最高）

`UBuildPreviewComponent::UpdatePreview` 每帧调 `FindNearestSnapCandidate`，后者每次都从零构建
`Occupied` / `Seen` 两个 `TSet` 加一个候选数组，遍历全部条目。

**修法**：候选集只在 `OnStructureChanged` 时重算一次并缓存在组件里，预览每帧只做"最近点查询"。
缓存按 `(SlotType, Level)` 分桶，或直接缓存 Floor/Level 0 这一种（当前唯一用到的组合）。

### 1.2 ISM 增量更新

`RebuildInstances` 现在 `ClearInstances()` 后重加全部实例。放一块 → 重建 N 个实例并弄脏渲染状态。

**修法**：维护 `EntryIndex → InstanceIndex` 映射，放置走 `AddInstance`，拆除走 `RemoveInstance`
（注意 `RemoveInstance` 会导致后续下标位移，需同步修正映射），或用
`BatchUpdateInstancesTransforms`。宿主移动本身不需要更新实例——实例是相对挂载点的。

### 1.3 批量恢复入口

存档恢复逐条调 `TryPlacePiece`，每条都整表重建索引与包围盒，并触发一次 `OnStructureChanged`
（进而重建一次 ISM）。1000 件 ≈ 50 万次索引插入 + 1000 次全量 ISM 重建，表现为读档卡死。

**修法**：新增 `BeginBatchEdit()` / `EndBatchEdit()`，批内跳过 `RebuildIndex`、
`NotifyStructureChanged`、`ForceNetUpdate`，结束时各做一次。

### 1.4 包围盒增量扩张

`ComputePieceBounds` 每次结构变化遍历全部条目。

**修法**：放置时只做 `Bounds += 新格`；拆除时才需要重算（且可以只在被拆格位于包围盒边界上时重算）。

### 1.5 连通性局部化

`WouldStayConnectedWithout` 每次拆除跑一次全图 flood fill。

**修法**：先做局部判断——若被拆格的四邻中，仍有格子彼此直接相邻或直接锚定，多数情况可直接放行；
只有可能切断图时才跑全量 BFS。或引入按结构版本号缓存的连通分量。

## 2. 宿主邻近门控（推荐，且解决另一处每帧开销）

**目标**：玩家不在任何可建造宿主附近时，建造能力等于不存在——按键无响应、无 UI 提示。

**不要用"授予 / 回收 Ability"实现。** 移除 ability spec 会打断正在激活的能力；玩家走到船边缘、
木筏随浪起伏都会让距离在阈值附近抖动，表现为建造模式被反复踢出。Lyra 自己的
`UAbilityTask_GrantNearbyInteraction` 也**只授予、从不回收**，正是在回避这个代价。

**推荐方案：常驻能力 + Tag 门控**

1. 能力仍由 PawnData 的 AbilitySet 授予一次（现状不变）。
2. 玩家侧加一个低频 timer（0.2~0.5s），直接问 `UBuildStructureSubsystem::FindNearestStructure`
   —— 注册表已经在手上，**不需要球形 overlap，无物理查询开销**。
3. 命中 → `AddLooseGameplayTag(Status.Build.HostAvailable)`；未命中 → 移除。
   带滞后：进入用 `R`，退出用 `R * 1.25`。
4. `GA_Build_Mode::CanActivateAbility` 增加该 Tag 条件；UI 订阅同一个 Tag 显示"按 B 建造"。

**顺带收益**：`UBuildPreviewComponent::FindBuildStructure` 目前每帧执行，内含一次
`GetHitResultUnderCursorByChannel` 光标射线。宿主改由 timer 维护并缓存后，预览每帧只剩
"光标投影到 Level 0 平面"这一步纯数学，射线可降到与 timer 同频。

## 3. 大世界的结构性问题（不是优化，是设计要定）

### 3.1 岛屿建筑必须按 Chunk 分宿主

木筏是移动 Actor，结构挂在它下面，几百件是合理上限。岛屿基地会是几千件且静止的。
若沿用"一个 Actor 持有全岛结构"：

- ISM 剔除是**整组件级别**的，远处也会全量提交
- 复制是 all-or-nothing，进入相关性就全量发

**正确做法**：每个 Chunk 一个 `IBuildStructureHost`，随 Chunk 激活 Spawn、卸载 Destroy，
远处只留存档不生成 Actor。这与 `Ocean-Island-Adventure-Design.md` 第 9 节的策略一致。
架构上已经预留（宿主接口与框架无关），**实现时不要按"岛"切，要按 Chunk 切**。

### 3.2 木筏不能简单改成休眠（更正）

早先本文写过"改成 `DORM_DormantAll` 是安全的，一行改动"，**这是错的**。木筏随浪持续运动，
客户端依赖 `ReplicatedMovement` 同步它的位置；一旦休眠，客户端上的船会冻住。
`FlushNetDormancy()` 只在结构变化时唤醒，救不了每帧的位移。

真正可行的路线有两条：

1. **降频而非休眠**：按到最近玩家的距离调整 `SetNetUpdateFrequency`，远处船降到几 Hz。
   现有的 `NetCullDistanceSquared`（1.5km）已经挡掉了更远的部分。
2. **客户端本地模拟浮力**：`OceanCore` 的海面采样是确定性的，客户端可以自己算出同样的姿态。
   做到这一步后木筏才具备休眠条件——只在结构变化和外力（推动、碰撞）时唤醒复制。
   这是设计层面的改动，不是一行。

### 3.3 浮力按距离降频（已完成）

`URaftBuoyancyComponent` 原本服务端每帧每船采样 4 个浮筒。现在按到最近玩家的距离分三档设置
`SetComponentTickInterval`：`FullRateDistance`（80m）内全速，`ReducedRateDistance`（250m）内
10Hz，更远 2Hz。距离本身每秒才重算一次，不是每帧。

**远处不停 tick 而是降到 2Hz**：完全停掉会让无人观察时漂流的木筏停在原地，玩家赶到时位置对不上。
UE 在节流的 tick 上传入累计 DeltaTime，所以插值仍与帧率无关。

### 3.4 静态建筑改用 HISM（接口已就位）

`IBuildStructureHost::GetInstancedMeshComponentClass()` 已加上，默认返回
`UInstancedStaticMeshComponent`；`UBuildStructureVisualComponent` 按宿主的回答创建组件。

`ARaftActor` 不覆写，继续用 ISM —— 这对移动宿主是正确选择，HISM 的簇树会随组件移动重建。
岛屿地基宿主实现时覆写为 `UHierarchicalInstancedStaticMeshComponent` 即可，**框架无需改动**。
