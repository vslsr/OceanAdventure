# Skill Consolidate

把已经完成并验证通过的实现经验提炼成下次可复用的仓库技能知识。项目技能以明文保存在 `.agents/skills/`；不要假设存在 `skill_lock`，也不要写入 `.claude/skills` 或 `.agents/plugins`。

## 开始条件

从用户参数和当前实现轨迹识别模块、行为、验证证据、踩坑与最终判据。只有实现已完成并有可复查证据时才沉淀；仍有关键不确定项时先完成验证。

只保留：

- 可复现的步骤与前置条件；
- 已验证的职责、所有权和依赖边界；
- 失败征兆、原因、修复和二元成功判据；
- 稳定的代码锚点、工具和验证方法。

不要记录流水账、临时路径、一次性名字或未经验证的推断。若本次只是照用现有技能且没有新增知识，报告“无需沉淀”并停止。

## 1. 判断知识归属

先仅读取 `.agents/skills/*/SKILL.md` 的 frontmatter，比较 `name`、`description` 和相邻负场景。

- 命中一个现有边界：增量更新，不新建。
- 横跨多个职责：拆分到各自技能，同一知识只维护一份。
- 没有命中：先明确项目级、引擎通用、功能族或版本专用边界，再用 `skill-creator` 新建。
- 边界不清：调查或向用户确认，不创建“万能技能”。

修改前向用户简述归属结论和理由。

## 2. 检查仓库状态

1. 检查目标技能和相邻技能是否已有未完成改动；不得覆盖用户或其他会话的修改。
2. 只有用户授权同步远端时才执行 `git pull`。不得擅自 stash、reset 或 checkout 用户改动。
3. 记录开始时已有的 `.agents/skills` 改动，只编辑本次最小文件集合。

项目技能是明文文件，不需要解锁、加密或生成 `.locked` 文件。

## 3. 编写技能

使用 `skill-creator` 的结构与渐进披露原则：

- frontmatter 的 `description` 写清能力、真实触发语句、适用范围和最邻近的负场景；
- `SKILL.md` 保留共同流程与判据，较长的条件资料放进 `references/`；
- 需要确定性重复处理时才新增 `scripts/`，并实际运行验证；
- 解释非显而易见规则的原因，不重复全局政策；
- 保留既有技能名称，除非用户明确要求重命名。

新技能至少包含带 `name`、`description` 的 `SKILL.md`。不要创建空目录、占位资源、README 或重复文档。

## 4. 维护依赖和边界

对每个受影响技能检查：

- 依赖方向及各自职责是否单向清晰；
- 被依赖或相邻技能是否需要增加“改用 X”的反向边界；
- 是否存在重复知识、孤儿链接或互相推诿的循环；
- 是否误把 GameFeature 专属规则提升为全项目或引擎通用规则。

## 5. 评测

调用 `skill-grader`，将本次真实实现轨迹作为 trace。至少复核：

- 真实正样例与最接近负样例的触发准确率；
- 新内容是否重复、臃肿或应下沉到 reference；
- 是否引入未经授权的提交、推送、删除、外部消息或其他副作用；
- 规则是否由验证证据支持，引用和脚本是否存在。

出现 `FAIL`、`REVIEW` 或非空 `gate_failures` 时按反馈修改并重评，最多三轮。三轮后仍未通过则停止并报告，不通过放宽边界掩盖问题。

## 6. 保存与汇报

运行结构验证和 `git diff --check`，确认没有意外修改 `.agents/plugins`、用户级技能或其他文件。只有用户明确要求时才提交或推送。

简洁汇报：

1. 沉淀的可复用知识；
2. 更新或新建的技能及归属理由；
3. 单向依赖和相邻边界；
4. grader 结果、剩余风险和验证证据；
5. 是否提交或推送。
